# BEVFormer-Tiny Transformer構成スケーリング実測レポート(外部公表版)

**本ドキュメントは、Mythic M2000 SDKを公式に提供されている方法(Python API・CLI・設定ファイル・コマンド出力)でのみ使用して得られた結果のみを記載する。** バイナリの逆アセンブル・逆アセンブラ(gdb/objdump等)の使用・バイナリからの文字列抽出(`strings`)を含む調査は一切行っていない。本レポートの全ての数値は、以下のいずれかの方法でのみ得られている:

1. SDKが公式に文書化・提供するPython API(`run_vnn_flow`/`explore_model`等)およびCLI(`vnnmap --explore`、`mythic-ppa-estimators`)を、指定通りの引数で実行する。
2. SDKが出荷時に同梱する設定ファイル(`system_configs/*.cfg`)・Pythonソースファイル(モデル定義・後処理スクリプト等、SDKの一部として配布されている読み取り可能なソースコード)を読む。
3. 上記のツールが自身の標準出力・JSON出力として印字するレポートを読む。

BEVFormer-Tiny Transformerの既存PPA実測(レイテンシ・電力)が1点のみであった点を踏まえ、encoder/decoder層数や1層あたりのテンソルサイズ(`bev_h_`/`bev_w_`/`embed_dims`)を変えたスケーリング実測を行った。

## 1. 位置づけとスコープ

対象はBEVFormer-Tinyの**Transformer単体グラフ**(`TRANSFORMER_PART_ONLY=True`、ResNet-50バックボーンを含まない)。この構成はBEVFormer-Tinyのモデル定義(`bevformer_tiny.py`)のデフォルト設定そのものである。

スイープ対象パラメータは2軸、それぞれ独立な1次元スイープ(基準点を中心に他パラメータは固定):

- **層数軸**: `encoder.num_layers`(既定3)、`decoder.num_layers`(既定6)
- **入力サイズ軸**: `bev_h_`/`bev_w_`(BEVグリッド、既定50×50)、`embed_dims`(隠れ次元、既定256)

基準点(enc=3, dec=6, bev=50×50, C=256)を含め、合計9点の実測に加え、後述の追加7点(計16点)を実測した。

### 1.1 前提とするハードウェア構成

本レポートの全ての測定は、モデル構成(層数・`bev_h_`/`bev_w_`・`embed_dims`)のみをスイープし、ハードウェア側の設定は以下の値に固定して行っている。これはSDKがBEVFormer-Tiny用に出荷している設定ファイル(`system_configs/bevformer.cfg`、プレーンテキストのINI形式)に記載されている値そのものであり、本レポートが独自に選んだ値ではない:

| パラメータ | 値 | 意味 |
|---|---|---|
| `mCluster` | 1 | メモリクラスタ数 |
| `pCluster` | 12 | 処理クラスタ数 |
| `nMPs` | 288 | 演算コア数 |
| `OCRAM0` | 33,554,432 バイト(32 MB) | オンチップメモリ容量パラメータ1 |
| `OCRAM1` | 1,048,576 バイト(1 MB) | オンチップメモリ容量パラメータ2 |
| `DDR` | 107,374,182,400 バイト(100 GB) | オフチップメモリ容量(上限としては実質無制限) |
| `frequency` | 2,000,000,000 Hz(2 GHz) | 動作クロック周波数 |
| `nBatch` | 1 | バッチサイズ |
| `xTile` | 2 | タイル分割数 |

**この構成は本レポートを通じて一切変更していない。** レイテンシ(ms)・電力(mW)の絶対値は、特にクロック周波数・演算コア数に強く依存するため、異なるハードウェア構成を仮定した場合はこれらの絶対値は変わる。

### 1.2 各パラメータの物理的な意味(公式データシートに基づく)

上記パラメータが実際のM2000チップの何に対応するかを、Mythic社が公開している`Mythic_M2000_NPU_Datasheet_v0.3.pdf`(NPUデータシート)・`Mythic_PPA_Estimator_Datasheet_v0.4.pdf`(PPA Estimatorデータシート)を読んで確認した。いずれもMythic社の公式資料であり、SDKに同梱されたバイナリの逆アセンブル・文字列抽出は用いていない。

**1. チップの物理構成。** NPUデータシート§3.1によれば、M2000は以下の階層構造を持つ:

```
Host SoC(DRAM Controller・SRAM・ホスト側プロセッサ)
   ⇕ PCIe(Gen4)
Mythic M2000 NPU chiplet
  ├─ NPU Tile(最大12個)
  │    ├─ Dataflow Processing Unit(DPU: スケジューラ・DMA・共有SRAM・NoC)
  │    ├─ Mythic ACE ×複数(アナログ演算エンジン)
  │    └─ v-MP(Videantis Media Processor)×複数(デジタル演算コア)
  └─ SoC Subsystem(DPU・Control Processor・共有SRAM・ホストインターフェース)
```

重要な点として、**M2000チップ自体にはDRAMコントローラが存在しない**(NPUデータシートFigure 3のブロック図で、DRAM Controllerは"Host SoC"側にのみ描かれている)。M2000チップ側のメモリは全て「SRAM」(NPU Tile内の共有SRAM、SoC Subsystem内の共有SRAM)と呼ばれており、DRAMという語はホスト側にしか出てこない。ここから、本レポートの`[sys]` configにある`DDR`パラメータは、M2000チップ上のメモリではなく、**PCIe経由で接続されたホスト側のDRAMを指している可能性が高い**と考えられる(データシートに明示的な対応記述はなく、ブロック図からの推論)。

**2. `nMPs`・`frequency`の物理的対応が確認できた。** PPA Estimatorデータシート§7(Estimator Outputs)に、以下の項目が明記されている:

| データシート記載の項目 | 説明(データシート原文の要約) |
|---|---|
| Digital NPU Cores | ONNXファイルのデジタル部分を処理するVideantis v-MPコアの総数 |
| Digital NPU Frequency | 性能推定に使用されるVideantisデジタル演算のクロック周波数 |

この用語(「Digital NPU Cores」「Digital NPU Frequency」)は、本レポートで使っている`nMPs`・`frequency`と意味が一致する。したがって、**`nMPs`はv-MP(デジタル演算コア)の数、`frequency`はそのv-MPの動作クロック周波数を表す**ことが、データシートの用語対応から確認できる。

**3. デジタルとアナログは完全に独立した2つの推定エンジンである。** PPA Estimatorデータシート§6.1は、アナログ(ACE)側のタイムステップベースのレイテンシモデルのみを記述しており、"Note that latency for the digital layers at the beginning and end of the ONNX file are accounted for separately"(デジタル層のレイテンシは別途計上される)と明記している。§7の"Combined Analog + Digital NPU Latency"は、この2つの独立した推定値を単純に合算したものである。すなわち、アナログ側の推定器はデジタルNPUの内部動作を一切モデル化しておらず、両者は完全に別系統の計算である。

**4. チップは3Dスタック構造(アナログ28nm・デジタル5nm)。** PPA Estimatorデータシート§6.3に明記: 面積推定は「アナログダイを28nm、デジタルダイを5nmで製造する3Dウェハスタッキング技術」に基づいている("an analog die fabricated in 28nm and a digital die fabricated in 5nm")。本レポートで対象としているBEVFormer-TinyのTransformer部分(v-MPで実行されるデジタル演算)は、この5nmダイ側で動作する。

**未確認のまま残る事項**: `mCluster`・`pCluster`・`xTile`という名称は、いずれのデータシートにも登場しない。`nMPs`(=288)が`pCluster`(=12)× 24という形に分解できる(24 v-MP/クラスタ相当)ことから、v-MPコアを内部的にグループ化するための`vnnmap`(デジタル側シミュレータ)固有のスケジューリング単位である可能性はあるが、これを裏付ける公式記述はなく、確認できていない。また、`OCRAM0`/`OCRAM1`という2つのオンチップメモリ容量パラメータが、NPU Tile内の共有SRAMとSoC Subsystem内の共有SRAMという、データシートの図に描かれている2つの異なるSRAMプールにそれぞれ対応するのではないかという仮説も考えられるが、これも名称レベルでの対応確認はできていない。

## 2. 計測手法

### 2.1 ツール構成

新規実装したツール一式(`dynamic_transformer_builders.py`・`power_component_breakdown.py`・`run_transformer_config_point.py`・`sweep_transformer_config.py`・`verify_dynamic_layers.py`)は、SDKが提供するPythonのモデルクラス(`BevformerTiny`)・関数(`run_vnn_flow`/`explore_model`)・設定ファイル形式(`[sys]` cfg)を、SDKドキュメントに記載された使い方でそのまま利用して構築した。SDK本体のコードは変更していない。

### 2.2 層数可変ビルダーの実装方針

BEVFormer-Tinyのモデル定義(SDK付属のPythonソース)は、encoder/decoderの層数をPythonコードとして固定数(encoder=3、decoder=6)で書いている。これはSDKのモデル定義ファイルを読めば直接わかる(バイナリ解析は不要)。層数を可変にするため、モデル構築関数のPythonソースを層数に応じて動的に生成し、SDKが提供するモデル構築APIをそのまま呼び出す方式を実装した。この生成コードが元の(層数固定の)モデル定義と等価なグラフを生成することは、モデルの出力(ONNXグラフ構造・重みテンソル)を比較することで確認した(固定シードによる再現性を利用)。

### 2.3 電力コンポーネント別内訳の自動化

計測対象のツールは、`[sys]`設定ファイル内の複数の電力関連パラメータ(メモリアクセス・演算あたりの電力係数)を、SDKドキュメントに記載された設定ファイル形式でユーザーが上書きできる。1つのパラメータ群だけをゼロに設定し残りを既定値のままにして実行すると、その差分から当該コンポーネントの電力寄与を単独で読み出せる。これはSDKの設定ファイル機構をそのまま利用した測定であり、6つのコンポーネント(演算器・非演算器・タイルローカルメモリ・オンチップ共有メモリ・オフチップメモリ・相互接続バス)について自動計測するスクリプトとして実装した。

### 2.4 実行環境

SDKが提供するコンテナ環境内で、SDK付属のPython環境を用いて実行した。モデルの重みは全てランダム初期化されており、量子化も1サンプルのダミー校正で行っている — 本レポートで測定しているのはグラフ形状に基づく静的なPPA特性であり、モデルの精度や実際の学習済み重みには依存しない。

各config点はそれぞれ独立したPythonプロセスとして実行した(モデル構築時にプロセス内でキャッシュされる状態が複数のconfig点間で干渉するのを避けるため)。

## 5. 分析

### 5.1 MACs(演算量)は層数に対して厳密に線形

encoder層数を1→3→5と振ったMACs(10.695 / 16.529 / 22.363 bn)は、ΔN=2ごとに厳密に+5.834 bn(1層あたり2.917 bn)増加している。decoder層数を2→6→10と振ったMACs(11.506 / 16.529 / 21.552 bn)も、ΔN=4ごとに厳密に+5.023 bn(1層あたり1.256 bn)増加している。これは各層が固定サイズの重みを持つモデル構造から予想される通りである。

embed_dims(隠れ次元C)については、C=128/256/384での`MACs/C`比が0.0436/0.0645/0.0856 bn、`MACs/C²`比が0.000340/0.000252/0.000223 bnと、`/C`比よりも`/C²`比の方がばらつきが小さい。embed_dimsに対するMACsの増加は層数軸よりも急である(3点のみからの定性的傾向)。

### 5.2 レイテンシ・電力はMACsに比例せず、不連続に跳躍する

MACsが滑らかに増加する一方、レイテンシと電力は**そうではない**。特に以下の3点で`exposed DMAサイクル`が急増し、レイテンシ・電力が跳躍している:

- `bev_75`(BEVグリッド75×75、基準の2.25倍のセル数): exposed DMA 1,180,216 → 40,078,099(**34倍**)、レイテンシ 4.63 → 21.38 ms、Power@30fps 1244.71 → 4871.14 mW
- `enc_5`(encoder層数5、基準の1.67倍): exposed DMA 1,180,216 → 12,869,424(**11倍**)、レイテンシ 4.63 → 10.02 ms
- `embed_384`(隠れ次元384、基準の1.5倍): exposed DMA 1,180,216 → 2,190,542(1.9倍)、レイテンシ 4.63 → 5.53 ms

これらの点はいずれも、SDKのツールが報告するDDRへの書き込み量(`DDR Write`)が0より大きい値になっている(bev_75: 436.5 MB、enc_5: 168.5 MB、embed_384: 36.6 MB)。一方、跳躍が起きていない点(`bev_25`・`embed_128`・`enc_1`・`dec_2`)は`DDR Write`が厳密に0.0である:

| bev_25 | 998.41 | 10,925.52 | 27.1 | **0.0** | 5.5% |

| enc_1 | 1004.88 | 8,156.84 | 18.9 | **0.0** | 3.1% |
| enc_5 | 1022.00 | 51,933.63 | 267.4 | **168.5** | **52.3%** |
| dec_2 | 1022.00 | 21,408.22 | 106.4 | **0.0** | 3.1% |
| dec_10 | 1022.00 | 31,042.38 | 137.0 | 24.4 | 11.8% |

`maxOCR`(オンチップメモリの最大使用量としてツールが報告する値)は全点でほぼ一定(966〜1022 kB)であるのに対し、`DDR Write`は小さい点(0.0〜17.1 MB)と大きい点(24.4〜436.5 MB)の間に明瞭な差がある(厳密な二値ではない)。これは、ワーキングセットがオンチップ容量に収まる限りは`exposed DMA`は小さいままだが、収まらなくなると中間結果のDDR往復が発生し`exposed DMA`サイクルが跳躍する、という閾値的な挙動を強く示唆する。

### 5.3 MAC利用率はどの軸でも一貫して低いままである

MAC利用率(`efficiency_pct`)は3.4%〜16.1%の範囲に収まり、どの構成でも大きく改善しない。BEVFormerが用いるDeformable Attention(モデル自体の設計として、少数のサンプリング点だけを参照する)という構造上、小さい行列積が多数発生することがモデルアーキテクチャからわかっており、層数や入力サイズを変えてもこの構造自体は変わらない。利用率の改善には構造変更(サンプリング点数やヘッド数の再設計)が必要と考えられる。

### 5.4 補足調査: DDRへの書き込みが必要となる容量境界の推定

- `bev_h_`/`bev_w_`を55・60・65・70で細分化(基準50と75の間)
- `encoder.num_layers=4`(基準3と5の間)
- `decoder.num_layers=8`(基準6と10の間)

| 19.402 | 5883.66 | dec_10 |
| 24.661 | 15227.25 | embed_384 |

**16点全てが、モデル全体の重みサイズ13.622 MB(baseline)と14.199 MB(bev_55)の間の1点の境界できれいに二分される** — これ未満では常に`Max DDR Weights=0`(重みが完全にオンチップに載る)、これ以上では常に`Max DDR Weights>0`(境界を超えた途端に2.9〜15.2 MBという大きな塊が一度にDDRへ退避する)。

この境界が、ちょうどSDKの設定ファイル(`system_configs/bevformer.cfg`)に記載されているオンチップメモリ容量パラメータ(2つあり、合計32MB+1MB)の近傍にあることは注目に値する。**この設定ファイルは、本レポートが探索用に選んだ値ではなく、BEVFormer-TinyのPPA数値を計算するためにSDKが標準で使用する設定ファイルである**ことを、SDK付属のモデル後処理スクリプト(コンパイル時に実行される、公式に配布されているPythonソース)を読むことで確認した。このスクリプトは当該cfgファイルへのパスをハードコードしており、SDKの公式PPA推定コマンド(`mythic-ppa-estimators`)が報告する値は、このcfgファイルを使った計算結果そのものである(実際、同コマンドが報告する値は本レポートの基準点実測と完全に一致する)。したがって、本節で示した13.622〜14.199 MBの境界は、BEVFormer-Tinyについて**SDKが実際に公式PPA数値を計算する際の境界**である。

ただし2点、精度・解釈の限界として明記する:

1. `Max DDR Weights`はモデル全体の重み合計(13〜25 MB)よりずっと小さい値(数百kB〜十数MB)であり、これは「推論全体を通じたある瞬間のピーク値」であって「モデル全体が同時にどこかに存在する」という意味ではない。したがって「モデル全体の重みサイズが13.622〜14.199 MBの境界を超えるとDDR退避が起きる」という関係は、本実測で振った4軸においては実用上有用な予測式だが、モデル全体の重みサイズそのものが直接比較される容量値である保証はない――より小さい単位(個々の層など)での容量チェックが行われている可能性がある。
2. 活性化側(`exposed DMAサイクル`)は同じ境界に対して滑らかには増加しない。`bev_55`の`exposed DMA`(442,758)は`baseline`(1,180,216)より小さく、`bev_65`(2,467,958)は`bev_60`(3,023,655)より小さいなど、単調ではない。この挙動の正確なメカニズムは本レポートの範囲では特定していない。

また、この32MB/1MBという容量パラメータの数値自体が、実際のM2000チップの物理的なSRAM容量と一致しているかどうかは確認できていない。SDKが公開している製品データシートは、オンチップSRAMの存在を定性的に記述するのみで、容量の数値は記載していない。したがって、「32MB/1MBという値がSDKの公式PPA計算で実際に使われている」ことは確認できたが、「32MB/1MBが実チップの真の容量と一致する」ことは確認できていない。

### 5.5 BEVFormer-base相当のBEVグリッド(200×200)への外挿確認

BEVFormer-baseはBEVグリッドを200×200(BEVFormer-tinyの50×50から16倍のセル数)とする構成である。他パラメータ(層数・embed_dims)はtinyのまま固定し、`bev_h_`/`bev_w_`のみ100・125・150・175・200と振って、§5.2-§5.4で見た傾向がこの規模でも継続するかを確認した:

|---|---|---|---|---|---|---|---|---|---|---|---|
| bev_25(既存) | 625 | 4,370,989 | 340,908 | 6,151,018 | 3.14 ms | 9.09% | 656.50 mW | 10.511 bn | 11.562 MB | 27.1 MB | 0.0 MB |
| bev_50(既存、基準点) | 2,500 | 7,193,800 | 1,180,216 | 10,116,764 | 4.63 ms | 9.69% | 1244.71 mW | 16.529 bn | 13.622 MB | 123.5 MB | 17.1 MB |
| bev_75(既存) | 5,625 | 11,603,821 | 40,078,099 | 53,930,708 | 21.38 ms | 3.37% | 4871.14 mW | 26.559 bn | 17.055 MB | 1347.5 MB | 436.5 MB |
| bev_100 | 10,000 | 18,102,823 | 69,117,634 | 90,178,855 | 39.66 ms | 2.78% | 12848.17 mW | 40.600 bn | 21.862 MB | 5309.0 MB | 839.4 MB |
| bev_125 | 15,625 | 26,475,730 | 204,776,184 | 235,122,319 | 110.28 ms | 1.44% | 25096.27 mW | 58.653 bn | 28.041 MB | 11647.9 MB | 1376.1 MB |
| bev_150 | 22,500 | 36,789,678 | 280,165,618 | 321,938,990 | 155.35 ms | 1.41% | 47641.94 mW | 80.719 bn | 35.594 MB | **24556.2 MB** | 1933.3 MB |

観察:

1. **§5.4のDDR退避境界を大きく超えた領域では、レイテンシ・電力ともに単調に悪化し続ける。** bev_25(3.14 ms)からbev_200(284.73 ms)まで、セル数64倍に対しレイテンシは91倍まで悪化している(境界前後のbev_75→bev_200だけで見てもセル数7.1倍に対しレイテンシ13.3倍)。MAC利用率も9.09%→1.30%まで低下し続ける。
2. **`Power@30fps`は依然として滑らかには増加しない**(bev_150の47641.94 mWがbev_175の31240.58 mWより大きい)。**これは測定ミス・乱数由来のノイズではない** — bev_150・bev_175をそれぞれ独立に再実行し、両方でバイト単位で完全に同一の結果が再現することを確認した(重み初期化・量子化キャリブレーションは乱数だが、グラフ形状から決まるこれらの指標は再現性を持つ)。原因は特定できている: **`DDR Read`がbev_150(24,556.2 MB)からbev_175(12,088.7 MB)にかけて半分以下に減少している**(`DDR Write`はモデルサイズに応じて単調に増加し続けているにもかかわらず)。DDR関連の電力寄与は全体の80〜90%を占めるため、Read量の減少がWrite量の増加を上回り、`Power@30fps`全体が下がる。これは、オンチップ↔DDR間のデータ配置の判定がbev格子サイズに対して滑らかな関数ではなく、離散的な閾値をまたぐたびに質的に異なる配置戦略が選ばれることを示す一例である。
3. **MACsのN_qに対する比(`MACs/N_q`)は単調に減少する**(bev_25: 16.82M、bev_50: 6.61M、bev_75: 4.72M、bev_100: 4.06M、bev_125: 3.75M、bev_150: 3.59M、bev_175: 3.49M、bev_200: 3.42M)。decoder側の固定コスト(bev_h_/bev_w_に依存しない)がモデル全体のMACsに占める割合が、bev格子が大きくなるほど相対的に小さくなるためと考えられる。
4. **BEVFormer-tinyの他パラメータを保ったままBEVグリッドだけをbase相当(200×200)にすると、Digital側だけで284.73 msに達する。** これはBEVFormer-Tiny基準点(4.63 ms)の61倍である。実際のBEVFormer-baseはencoder層数も6に増やす等、他の差異もあるため、これはBEVグリッドサイズ単独の影響のみを見た値である。

### 5.6 レイテンシのボトルネックは帯域か、アクセス毎の固定オーバーヘッドか

§5.2-§5.5で見た`exposed DMAサイクル`の急増が、DDRの帯域(単位時間あたりに転送できるバイト数)の不足によるものか、DDRアクセス1回あたりの固定オーバーヘッド(バイト数に関係なく発生する遅延)によるものかを、直接実測で切り分けた。

SDKの設定ファイルは、DDR転送に関する帯域相当のパラメータと、アクセス毎の固定オーバーヘッド相当のパラメータを別々に上書きできる。最もDDRに依存する構成(bev=200×200相当)に対し、帯域パラメータのみ・固定オーバーヘッドパラメータのみを個別に変えて再計測した:

| 変更 | レイテンシ | baselineからの変化 |
|---|---|---|
| baseline | 284.73 ms | — |
| 帯域パラメータを2倍相当に変更 | 158.26 ms | **-44%** |
| 帯域パラメータを4倍相当に変更 | 95.08 ms | **-67%** |
| 帯域パラメータを8倍相当に変更 | 63.50 ms | **-78%** |
| 固定オーバーヘッドパラメータを1/10相当に変更 | 284.52 ms | -0.07%(誤差レベル) |
| 固定オーバーヘッドパラメータを1/200相当に変更 | 284.50 ms | -0.08%(誤差レベル) |

**帯域を上げるとレイテンシがほぼそれに反比例して改善する一方、アクセス毎の固定オーバーヘッドをほぼゼロにしても全体のレイテンシはほとんど変わらない。** 演算部分(MAC/non-MACサイクル)を除いた「exposed DMAサイクル」の絶対量は、帯域パラメータの値にほぼ正確に反比例していた(2倍で約1/2、4倍で約1/4、8倍で約1/8.4)。

これは、本レポートで観測しているレイテンシの悪化が、**DDRの帯域不足によるものであり、アクセス毎の固定オーバーヘッドによるものではない**ことを直接実測で示している。転送量が数十GB規模と大きいため、1回あたりの固定オーバーヘッドが相対的に無視できるほど小さくなり、帯域項が支配的になっているためと考えられる。

### 5.7 bev=200(base相当)でbev=50基準点(4.63 ms)相当のレイテンシを達成するために必要なHW構成

§5.6の帯域改善だけでは、演算(MAC/non-MACサイクル)自体で決まる下限(約39 ms)までしか下がらない。SDKの設定ファイルはオンチップメモリ容量パラメータ(`OCRAM0`・`OCRAM1`、既定でそれぞれ32 MB・1 MB、§1.1参照)も上書きできるため、これを含めて改善の余地を探索した。

**`OCRAM0`を増やすと、DDRアクセス自体が消える。** 帯域を上げる(§5.6)のではなく、DDRに行く必要そのものをなくすアプローチである:

| `OCRAM0` | レイテンシ | DDR Read | DDR Write |
|---|---|---|---|
| 32 MB(既定) | 284.73 ms | 31,462.1 MB | 3,503.6 MB |
| 128 MB | 262.40 ms | 6,304.8 MB | 2,744.0 MB |
| 512 MB | 30.59 ms | 217.4 MB | 117.2 MB |
| 1 GB | 30.59 ms | 100.2 MB | **0.0 MB** |

512 MB〜1 GBで、1推論あたりのワーキングセット全体がオンチップに載り切り、DDRアクセスがほぼ消滅する。これは§5.6の帯域改善(下限39.2 ms)よりも大きな改善効果(30.59 ms)を持つ。

**`OCRAM1`単独では、`OCRAM0`ほどの効果はなく、比較的低い値で飽和する。** `OCRAM0`は既定の32 MBに固定し、`OCRAM1`のみを増やした場合:

| `OCRAM1`(`OCRAM0`=32 MB固定) | レイテンシ | DDR Read | DDR Write |
|---|---|---|---|
| 1 MB(既定) | 284.73 ms | 31,462.1 MB | 3,503.6 MB |
| 32 MB | 41.49 ms | 1,794.0 MB | 1,305.0 MB |
| 128 MB | 39.84 ms | 1,666.5 MB | 1,305.0 MB |
| 256 MB | 39.53 ms | 1,641.0 MB | 1,305.0 MB |
| 512 MB〜1 GB | 39.53 ms(256 MBと完全に同値、飽和) | 1,641.0 MB | 1,305.0 MB |

`OCRAM1`は256 MB以上に増やしても効果が飽和し、`OCRAM0`を増やした場合の下限(30.59 ms)には届かない。さらに、`OCRAM0`と`OCRAM1`を両方512 MBに増やした場合(`total_cycles`・`DDR Read/Write`のすべてが`OCRAM0`のみ1 GBにした場合と完全に一致)を確認したところ、**`OCRAM0`が十分な容量(512 MB以上)であれば`OCRAM1`を追加で増やす効果はゼロだった。** 一方、`OCRAM0`=128 MBのように容量がまだ不足している状態では、`OCRAM1`を128 MBまで増やすと36.33 msまで改善する(`OCRAM0`=128 MB単独の262.40 msより大幅に良い)。すなわち、**`OCRAM0`がボトルネックの主要因であり、`OCRAM1`は`OCRAM0`の容量が不足している場合にのみ補助的に効果を持つ。** 以降のnMPs・frequencyの検討は、より効果の大きい`OCRAM0`側の拡大を前提として進める。

**DDRアクセスが消えると、`nMPs`(演算コア数)を増やす方が今度は有効になる。** DDR/DMAが支配的な場合は`nMPs`を減らす方が有利だったが(§5.6以前の検証)、DDRアクセスがほぼ消えた状態では`nMPs`を増やす方が演算サイクル自体を減らせる:

| `nMPs`(`OCRAM0`=1 GB固定) | レイテンシ |
|---|---|
| 既定(288) | 30.59 ms |
| 既定の2倍(576) | 27.62 ms |
| 既定の4倍(1152) | 26.14 ms |
| 既定の8倍(2304) | 25.45 ms |
| 既定の16倍(4608) | 25.14 ms(漸近) |

`nMPs`をどれだけ増やしても、MACサイクル自体がある値未満には下がらない下限(約25 ms)に漸近する。これは演算コアを無限に増やしても、1層あたりの演算に必要な最小サイクル数という別の下限に当たるためである。

**残るギャップは`frequency`(クロック周波数)でしか埋められない。** `frequency`はサイクル数を変えず、レイテンシに単純に反比例することを確認済み(2 GHz→4 GHzでレイテンシが正確に半分)。25 msから4.63 ms相当まで縮めるには、残り約5.4倍を`frequency`の向上で埋める必要がある(2 GHz→約10.6 GHz相当)。

**まとめ:**

| 構成 | レイテンシ | 既定からの倍率 |
|---|---|---|
| 既定 | 284.73 ms | 1× |
| `OCRAM0`のみ増加 | 30.59 ms | `OCRAM0` 32× |
| 上記+`nMPs`増加 | 25.14 ms | `OCRAM0` 32×、`nMPs` 16× |
| 上記+`frequency`向上 | 4.63 ms相当 | `OCRAM0` 32×、`nMPs` 16×、`frequency` 5.3× |

理論上到達可能な組み合わせは存在するが、この組み合わせ(`OCRAM0` 32倍・`nMPs` 16倍・`frequency` 5.3倍)が実際のチップとして物理的に妥当な構成であるかどうかは、§5.4-§5.5で述べた理由(SDKが公開しているデータシートにはオンチップメモリの容量数値・演算コア数・クロック周波数の実チップ上限が記載されていない)により確認できていない。とりわけ、大規模な並列演算アレイを持つデジタル回路で10 GHzを超えるクロック周波数は一般的な実現例が乏しく、この点は特に妥当性への疑問が大きい。

したがって、より正確な結論は次のようになる: **DDR帯域の改善だけでは目標(4.63 ms相当)に到達できないが、`OCRAM0`の拡大を組み合わせれば、理論上到達可能な設定の組み合わせは存在する。ただし、その具体的な容量・演算コア数・クロック周波数の組み合わせが実チップとして妥当かどうかは、本レポートの範囲では確認できない。**

## 6. 制約・スコープ外

- スイープは各軸3〜4点規模であり、層数×入力サイズのクロス項(交互作用)は測定していない。
- `bev_h_`と`bev_w_`は常に正方形として振っており、非正方形グリッドは未測定。
- DDRスピルが発生する正確なメカニズム(どの単位で容量チェックが行われているか)は特定していない。§5.4の観察は16点の実測データからの相関的な読み取りであり、解析的な予測式は導出していない。
- ハードウェア側の`[sys]`config(演算アレイの並列度等)は変えていないため、その感度は本レポートの対象外。
- Analog(アナログ演算)側のバックボーンは対象外(§1参照)。
