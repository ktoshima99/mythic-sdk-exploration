# BEVFormer-Tiny Transformer構成スケーリング実測レポート(外部公表版)

**本ドキュメントは、Mythic M2000 SDKを公式に提供されている方法(Python API・CLI・設定ファイル・コマンド出力)でのみ使用して得られた結果のみを記載する。** バイナリの逆アセンブル・逆アセンブラ(gdb/objdump等)の使用・バイナリからの文字列抽出(`strings`)を含む調査は一切行っていない。本レポートの全ての数値は、以下のいずれかの方法でのみ得られている:

1. SDKが公式に文書化・提供するPython API(`run_vnn_flow`/`explore_model`等)およびCLI(`vnnmap --explore`、`mythic-ppa-estimators`)を、指定通りの引数で実行する。
2. SDKが出荷時に同梱する設定ファイル(`system_configs/*.cfg`)・Pythonソースファイル(モデル定義・後処理スクリプト等、SDKの一部として配布されている読み取り可能なソースコード)を読む。
3. 上記のツールが自身の標準出力・JSON出力として印字するレポートを読む。

BEVFormer-Tiny Transformerの既存PPA実測(レイテンシ・電力)が1点のみであった点を踏まえ、encoder/decoder層数や1層あたりのテンソルサイズ(`bev_h_`/`bev_w_`/`embed_dims`)を変えたスケーリング実測を行った。

## 1. 位置づけとスコープ

対象はBEVFormer-Tinyの**Transformer単体グラフ**(`TRANSFORMER_PART_ONLY=True`、ResNet-50バックボーンを含まない)。この構成はBEVFormer-Tinyのモデル定義(`bevformer_tiny.py`)のデフォルト設定そのものである。

スイープ対象パラメータは2軸、それぞれ独立な1次元スイープ(基準点を中心に他パラメータは固定):

- **層数軸**: `encoder.num_layers`(既定3)、`decoder.num_layers`(既定6)
- **入力サイズ軸**: `bev_h_`/`bev_w_`(BEVグリッド、既定50×50)、`embed_dims`(隠れ次元、既定256)

基準点(enc=3, dec=6, bev=50×50, C=256)を含め、合計9点の実測に加え、後述の追加7点(計16点)を実測した。

### 1.1 前提とするハードウェア構成

本レポートの全ての測定は、モデル構成(層数・`bev_h_`/`bev_w_`・`embed_dims`)のみをスイープし、ハードウェア側の設定は以下の値に固定して行っている。これはSDKがBEVFormer-Tiny用に出荷している設定ファイル(`system_configs/bevformer.cfg`、プレーンテキストのINI形式)に記載されている値そのものであり、本レポートが独自に選んだ値ではない:

| パラメータ | 値 | 意味 |
|---|---|---|
| `mCluster` | 1 | メモリクラスタ数 |
| `pCluster` | 12 | 処理クラスタ数 |
| `nMPs` | 288 | 演算コア数 |
| `OCRAM0` | 33,554,432 バイト(32 MB) | オンチップメモリ容量パラメータ1 |
| `OCRAM1` | 1,048,576 バイト(1 MB) | オンチップメモリ容量パラメータ2 |
| `DDR` | 107,374,182,400 バイト(100 GB) | オフチップメモリ容量(上限としては実質無制限) |
| `frequency` | 2,000,000,000 Hz(2 GHz) | 動作クロック周波数 |
| `nBatch` | 1 | バッチサイズ |
| `xTile` | 2 | タイル分割数 |

**この構成は本レポートを通じて一切変更していない。** レイテンシ(ms)・電力(mW)の絶対値は、特にクロック周波数・演算コア数に強く依存するため、異なるハードウェア構成を仮定した場合はこれらの絶対値は変わる。

## 2. 計測手法

### 2.1 ツール構成

新規実装したツール一式(`dynamic_transformer_builders.py`・`power_component_breakdown.py`・`run_transformer_config_point.py`・`sweep_transformer_config.py`・`verify_dynamic_layers.py`)は、SDKが提供するPythonのモデルクラス(`BevformerTiny`)・関数(`run_vnn_flow`/`explore_model`)・設定ファイル形式(`[sys]` cfg)を、SDKドキュメントに記載された使い方でそのまま利用して構築した。SDK本体のコードは変更していない。

### 2.2 層数可変ビルダーの実装方針

BEVFormer-Tinyのモデル定義(SDK付属のPythonソース)は、encoder/decoderの層数をPythonコードとして固定数(encoder=3、decoder=6)で書いている。これはSDKのモデル定義ファイルを読めば直接わかる(バイナリ解析は不要)。層数を可変にするため、モデル構築関数のPythonソースを層数に応じて動的に生成し、SDKが提供するモデル構築APIをそのまま呼び出す方式を実装した。この生成コードが元の(層数固定の)モデル定義と等価なグラフを生成することは、モデルの出力(ONNXグラフ構造・重みテンソル)を比較することで確認した(固定シードによる再現性を利用)。

### 2.3 電力コンポーネント別内訳の自動化

計測対象のツールは、`[sys]`設定ファイル内の複数の電力関連パラメータ(メモリアクセス・演算あたりの電力係数)を、SDKドキュメントに記載された設定ファイル形式でユーザーが上書きできる。1つのパラメータ群だけをゼロに設定し残りを既定値のままにして実行すると、その差分から当該コンポーネントの電力寄与を単独で読み出せる。これはSDKの設定ファイル機構をそのまま利用した測定であり、6つのコンポーネント(演算器・非演算器・タイルローカルメモリ・オンチップ共有メモリ・オフチップメモリ・相互接続バス)について自動計測するスクリプトとして実装した。

### 2.4 実行環境

SDKが提供するコンテナ環境内で、SDK付属のPython環境を用いて実行した。モデルの重みは全てランダム初期化されており、量子化も1サンプルのダミー校正で行っている — 本レポートで測定しているのはグラフ形状に基づく静的なPPA特性であり、モデルの精度や実際の学習済み重みには依存しない。

各config点はそれぞれ独立したPythonプロセスとして実行した(モデル構築時にプロセス内でキャッシュされる状態が複数のconfig点間で干渉するのを避けるため)。

## 5. 分析

### 5.1 MACs(演算量)は層数に対して厳密に線形

encoder層数を1→3→5と振ったMACs(10.695 / 16.529 / 22.363 bn)は、ΔN=2ごとに厳密に+5.834 bn(1層あたり2.917 bn)増加している。decoder層数を2→6→10と振ったMACs(11.506 / 16.529 / 21.552 bn)も、ΔN=4ごとに厳密に+5.023 bn(1層あたり1.256 bn)増加している。これは各層が固定サイズの重みを持つモデル構造から予想される通りである。

embed_dims(隠れ次元C)については、C=128/256/384での`MACs/C`比が0.0436/0.0645/0.0856 bn、`MACs/C²`比が0.000340/0.000252/0.000223 bnと、`/C`比よりも`/C²`比の方がばらつきが小さい。embed_dimsに対するMACsの増加は層数軸よりも急である(3点のみからの定性的傾向)。

### 5.2 レイテンシ・電力はMACsに比例せず、不連続に跳躍する

MACsが滑らかに増加する一方、レイテンシと電力は**そうではない**。特に以下の3点で`exposed DMAサイクル`が急増し、レイテンシ・電力が跳躍している:

- `bev_75`(BEVグリッド75×75、基準の2.25倍のセル数): exposed DMA 1,180,216 → 40,078,099(**34倍**)、レイテンシ 4.63 → 21.38 ms、Power@30fps 1244.71 → 4871.14 mW
- `enc_5`(encoder層数5、基準の1.67倍): exposed DMA 1,180,216 → 12,869,424(**11倍**)、レイテンシ 4.63 → 10.02 ms
- `embed_384`(隠れ次元384、基準の1.5倍): exposed DMA 1,180,216 → 2,190,542(1.9倍)、レイテンシ 4.63 → 5.53 ms

これらの点はいずれも、SDKのツールが報告するDDRへの書き込み量(`DDR Write`)が0より大きい値になっている(bev_75: 436.5 MB、enc_5: 168.5 MB、embed_384: 36.6 MB)。一方、跳躍が起きていない点(`bev_25`・`embed_128`・`enc_1`・`dec_2`)は`DDR Write`が厳密に0.0である:

|---|---|---|---|---|---|
| baseline | 1022.00 | 23,908.22 | 123.5 | 17.1 | 11.7% |
| bev_25 | 998.41 | 10,925.52 | 27.1 | **0.0** | 5.5% |
| bev_75 | 972.56 | 80,016.80 | 1347.5 | **436.5** | **74.3%** |
| embed_128 | 966.50 | 13,633.22 | 15.1 | **0.0** | 4.5% |
| embed_384 | 987.17 | 58,585.53 | 527.5 | **36.6** | 20.1% |
| enc_1 | 1004.88 | 8,156.84 | 18.9 | **0.0** | 3.1% |
| enc_5 | 1022.00 | 51,933.63 | 267.4 | **168.5** | **52.3%** |
| dec_2 | 1022.00 | 21,408.22 | 106.4 | **0.0** | 3.1% |
| dec_10 | 1022.00 | 31,042.38 | 137.0 | 24.4 | 11.8% |

`maxOCR`(オンチップメモリの最大使用量としてツールが報告する値)は全点でほぼ一定(966〜1022 kB)であるのに対し、`DDR Write`は小さい点(0.0〜17.1 MB)と大きい点(24.4〜436.5 MB)の間に明瞭な差がある(厳密な二値ではない)。これは、ワーキングセットがオンチップ容量に収まる限りは`exposed DMA`は小さいままだが、収まらなくなると中間結果のDDR往復が発生し`exposed DMA`サイクルが跳躍する、という閾値的な挙動を強く示唆する。

### 5.3 MAC利用率はどの軸でも一貫して低いままである

MAC利用率(`efficiency_pct`)は3.4%〜16.1%の範囲に収まり、どの構成でも大きく改善しない。BEVFormerが用いるDeformable Attention(モデル自体の設計として、少数のサンプリング点だけを参照する)という構造上、小さい行列積が多数発生することがモデルアーキテクチャからわかっており、層数や入力サイズを変えてもこの構造自体は変わらない。利用率の改善には構造変更(サンプリング点数やヘッド数の再設計)が必要と考えられる。

### 5.4 補足調査: DDRへの書き込みが必要となる容量境界の推定

§5.2で見た`exposed DMAサイクル`の跳躍が、モデル全体の重みサイズと関連しているという仮説を検証するため、以下の追加実測を行った:

- `bev_h_`/`bev_w_`を55・60・65・70で細分化(基準50と75の間)
- `encoder.num_layers=4`(基準3と5の間)
- `decoder.num_layers=8`(基準6と10の間)
- `embed_dims=320`(基準256と384の間)

SDKのツールは、DDRに退避が必要になった重みの量(`Max DDR Weights`)を出力として報告する。全16点(元の9点+追加7点)を`Model Size (MB)`(モデル全体の静的重みサイズ、こちらもツールが直接報告する値)でソートすると、4つの軸(層数・BEVサイズ・embed_dims)を横断して極めて明瞭な境界が現れる:

| 7.842 | 0.00 | dec_2 |
| 10.495 | 0.00 | enc_1 |
| 11.562 | 0.00 | bev_25 |
| **13.622** | **0.00** | **baseline** |
| **14.199** | **6485.50** | **bev_55** |

**16点全てが、モデル全体の重みサイズ13.622 MB(baseline)と14.199 MB(bev_55)の間の1点の境界できれいに二分される** — これ未満では常に`Max DDR Weights=0`(重みが完全にオンチップに載る)、これ以上では常に`Max DDR Weights>0`(境界を超えた途端に2.9〜15.2 MBという大きな塊が一度にDDRへ退避する)。

この境界が、ちょうどSDKの設定ファイル(`system_configs/bevformer.cfg`)に記載されているオンチップメモリ容量パラメータ(2つあり、合計32MB+1MB)の近傍にあることは注目に値する。**この設定ファイルは、本レポートが探索用に選んだ値ではなく、BEVFormer-TinyのPPA数値を計算するためにSDKが標準で使用する設定ファイルである**ことを、SDK付属のモデル後処理スクリプト(コンパイル時に実行される、公式に配布されているPythonソース)を読むことで確認した。このスクリプトは当該cfgファイルへのパスをハードコードしており、SDKの公式PPA推定コマンド(`mythic-ppa-estimators`)が報告する値は、このcfgファイルを使った計算結果そのものである(実際、同コマンドが報告する値は本レポートの基準点実測と完全に一致する)。したがって、本節で示した13.622〜14.199 MBの境界は、BEVFormer-Tinyについて**SDKが実際に公式PPA数値を計算する際の境界**である。

ただし2点、精度・解釈の限界として明記する:

1. `Max DDR Weights`はモデル全体の重み合計(13〜25 MB)よりずっと小さい値(数百kB〜十数MB)であり、これは「推論全体を通じたある瞬間のピーク値」であって「モデル全体が同時にどこかに存在する」という意味ではない。したがって「モデル全体の重みサイズが13.622〜14.199 MBの境界を超えるとDDR退避が起きる」という関係は、本実測で振った4軸においては実用上有用な予測式だが、モデル全体の重みサイズそのものが直接比較される容量値である保証はない――より小さい単位(個々の層など)での容量チェックが行われている可能性がある。
2. 活性化側(`exposed DMAサイクル`)は同じ境界に対して滑らかには増加しない。`bev_55`の`exposed DMA`(442,758)は`baseline`(1,180,216)より小さく、`bev_65`(2,467,958)は`bev_60`(3,023,655)より小さいなど、単調ではない。この挙動の正確なメカニズムは本レポートの範囲では特定していない。

また、この32MB/1MBという容量パラメータの数値自体が、実際のM2000チップの物理的なSRAM容量と一致しているかどうかは確認できていない。SDKが公開している製品データシートは、オンチップSRAMの存在を定性的に記述するのみで、容量の数値は記載していない。したがって、「32MB/1MBという値がSDKの公式PPA計算で実際に使われている」ことは確認できたが、「32MB/1MBが実チップの真の容量と一致する」ことは確認できていない。

| **bev_200(base相当)** | **40,000** | 55,990,817 | 536,795,362 | 600,607,131 | **284.73 ms** | 1.30% | **64966.31 mW** | 136.884 bn | 54.821 MB | 3503.6 MB |

観察:

1. **§5.4のDDR退避境界を大きく超えた領域では、レイテンシ・電力ともに単調に悪化し続ける。** bev_75(21.38 ms)からbev_200(284.73 ms)まで、セル数7.1倍に対しレイテンシは13.3倍まで悪化している。MAC利用率も3.37%→1.30%まで低下し続ける。
2. **`Power@30fps`は依然として滑らかには増加しない。** bev_150(47641.94 mW)がbev_175(31240.58 mW)より大きいなど、§5.4で確認した非単調性がこの規模でも再現している。
3. **MACsのN_qに対する比(`MACs/N_q`)は単調に減少する**(bev_75: 4.72M、bev_100: 4.06M、bev_125: 3.75M、bev_150: 3.59M、bev_175: 3.49M、bev_200: 3.42M)。decoder側の固定コスト(bev_h_/bev_w_に依存しない)がモデル全体のMACsに占める割合が、bev格子が大きくなるほど相対的に小さくなるためと考えられる。
4. **BEVFormer-tinyの他パラメータを保ったままBEVグリッドだけをbase相当(200×200)にすると、Digital側だけで284.73 msに達する。** これはBEVFormer-Tiny基準点(4.63 ms)の61倍である。実際のBEVFormer-baseはencoder層数も6に増やす等、他の差異もあるため、これはBEVグリッドサイズ単独の影響のみを見た値である。

## 6. 制約・スコープ外

- スイープは各軸3〜4点規模であり、層数×入力サイズのクロス項(交互作用)は測定していない。
- `bev_h_`と`bev_w_`は常に正方形として振っており、非正方形グリッドは未測定。
- DDRスピルが発生する正確なメカニズム(どの単位で容量チェックが行われているか)は特定していない。§5.4の観察は16点の実測データからの相関的な読み取りであり、解析的な予測式は導出していない。
- ハードウェア側の`[sys]`config(演算アレイの並列度等)は変えていないため、その感度は本レポートの対象外。
- Analog(アナログ演算)側のバックボーンは対象外(§1参照)。
